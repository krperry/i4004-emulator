Lesson 2: Hello, World on a 4-Bit Chip

Almost every programmer's first program makes the computer say hello. On a modern computer that takes one line. On the 4004 it takes a little more thought, because the chip can only send out 4 bits at a time, and a letter needs 8. In this lesson you will walk through examples/hello.asm one line at a time. You will see the bytes each line becomes and what the chip does when it runs them.

Topics covered in this lesson

  • How text is stored as bytes
  • How a 4-bit chip prints an 8-bit letter
  • Loading a byte from ROM with FIN
  • Choosing a port with SRC and writing to it with WRR
  • Making decisions with JCN
  • Counting with ISZ and carrying into the next nibble
  • Stopping a chip that has no stop instruction

What the Program Does

Run it first, so you know what you are aiming for:

python -m i4004 run examples/hello.asm --console --accessible

You will hear:

Output: HELLO, WORLD! THE 4004 TURNS 55 TODAY.

Then the emulator tells you the chip stopped at hex 015 after 453 instruction cycles. That is about 4.9 thousandths of a second on a real 4004.

The program does three things. It picks the port to print on. It walks through a message stored in ROM, one byte at a time, sending each byte to the port. It stops when it reaches a byte of 0, which marks the end of the message.

How Letters Become Bytes

Computers store each letter as a number, using a standard table called ASCII. In ASCII, capital H is 72, which is hex 48. Capital E is hex 45, a space is hex 20, and a new line is hex 0A. So the message is really just a list of bytes:

48 45 4C 4C 4F 2C 20 57 ...

That is H, E, L, L, O, comma, space, W, and so on.

How a 4-Bit Chip Prints an 8-Bit Letter

The 4004's accumulator holds one nibble. Its WRR instruction writes that one nibble to a port. There is no way to send a whole byte at once.

So the program sends every letter in two halves. First it sends the high nibble, then the low nibble. To print H, which is hex 48, it writes 4 and then 8. The emulator's --console option makes ROM port 0 act like a terminal that understands this. It holds on to the first nibble it gets, and when the second one arrives it joins them into a byte and prints that letter.

Real 4004 systems did the same kind of thing. The Busicom calculator sent its printer and display data out through 4-bit ports, a piece at a time.

The Whole Program

Here is the listing the assembler makes. It shows the address and bytes for each line, followed by the source. The comment lines at the top of the file are left out.

000  22 00   start:  FIM  P1, 0x00
002  23              SRC  P1
003  20 17           FIM  P0, msg
005  34      loop:   FIN  P2
006  A4              LD   R4
007  1C 0C           JNZ  emit
009  A5              LD   R5
00A  14 15           JZ   done
00C  A4      emit:   LD   R4
00D  E2              WRR
00E  A5              LD   R5
00F  E2              WRR
010  71 05           ISZ  R1, loop
012  60              INC  R0
013  40 05           JUN  loop
015  40 15   done:   JUN  done
017  48 45 4C ...   msg: DB "HELLO, WORLD! THE 4004 TURNS 55 TODAY.", 10, 0

To get the same listing yourself, type:

python -m i4004 asm examples/hello.asm --listing --accessible

The whole program, message included, is 63 bytes. Now let's go through it one line at a time. Each line has its own heading below.

Part 1: Choosing the Port

Address 000: start: FIM P1, 0x00

Bytes: hex 22, then hex 00.

FIM means fetch immediate. It loads a whole byte into a register pair. This line puts hex 00 into pair P1, which means R2 becomes 0 and R3 becomes 0. The label start just names this address. Nothing in the program jumps to it, but it makes the listing easier to read.

How the bytes are built: the first byte, hex 22, is 0010 0010 in binary. The high nibble, 2, is the code for the FIM and SRC family. In the low nibble, the first three bits, 001, are the pair number, 1. The last bit is 0, which means FIM, not SRC. The second byte, hex 00, is the data to load.

Address 002: SRC P1

Byte: hex 23.

SRC sends the byte in a register pair out as the address for the next RAM or port instruction. P1 holds hex 00. For a ROM port, the high nibble of the address is the port number, so this picks ROM port 0. That is the port the console listens on. The program never sends a different address, so every WRR after this goes to port 0.

Hex 23 is the same as the FIM byte above, except the last bit is 1. That one bit is the only difference between FIM P1 and SRC P1.

Address 003: FIM P0, msg

Bytes: hex 20, then hex 17.

This loads the address of the message into pair P0. The label msg is at address hex 017, so R0 becomes 1 and R1 becomes 7. P0 is now a pointer. It holds the address of the next letter to print. The assembler worked out the 17 for us from the label. That is one of the main jobs of an assembler.

Why P0? The FIN instruction coming up always takes its address from pair P0. You don't get to choose.

Part 2: Fetching a Letter and Checking for the End

Address 005: loop: FIN P2

Byte: hex 34.

FIN means fetch indirect. It reads a byte from ROM, from the address held in P0, and puts it into the pair named in the instruction, here P2. The first time round, P0 is hex 17, so it reads the byte at address hex 017. That byte is hex 48, the letter H. So R4 becomes 4 and R5 becomes 8.

FIN has only 8 bits of address in P0, so it reads from the current ROM page. This instruction is in page 0, so it can reach addresses hex 000 to hex 0FF. The message has to fit in that range.

The label loop marks the top of the loop. The program comes back here for every letter. FIN takes two instruction cycles, because the chip has to make a second trip to ROM to fetch the data.

Address 006: LD R4

Byte: hex A4. A means LD, load, and 4 means register R4.

This copies R4, the high nibble of the letter, into the accumulator. The next instruction can only test the accumulator, so the value has to be there first.

Address 007: JNZ emit

Bytes: hex 1C, then hex 0C.

JNZ means jump if not zero. If the accumulator is not 0, the program jumps to emit at address hex 00C. If it is 0, it goes on to the next line. For H, the accumulator is 4, so it jumps.

The 4004 does not really have a JNZ instruction. This assembler accepts it as a friendly name for JCN, jump conditional, with a condition code. Here is how the bytes work. The 1 in hex 1C means JCN. The C, which is 1100 in binary, is the condition. Its bit for 4 means test whether the accumulator is zero. Its bit for 8 means turn the test around. So together they mean jump if the accumulator is not zero.

The second byte, hex 0C, is only the low 8 bits of the address. The chip keeps the page part of its current address and just swaps in these 8 bits. That is why JCN can only jump within the current page. The assembler checks this for you and gives an error if a target is too far away.

Address 009: LD R5

Byte: hex A5.

The program only gets here if the high nibble was 0. Now it loads the low nibble to check that one too.

Why check both? The end of the message is marked with a byte of 0, so both nibbles must be 0. But some real characters also have a high nibble of 0. The new line character, hex 0A, is one of them. If the program only checked the high nibble, it would stop at the new line and never print it.

Address 00A: JZ done

Bytes: hex 14, then hex 15.

JZ means jump if zero. It is JCN with condition 4, which tests whether the accumulator is zero without turning the test around. If the low nibble is also 0, this is the end marker, so the program jumps to done at hex 015. Otherwise it falls through into emit, the next line.

Part 3: Printing the Letter

Address 00C: emit: LD R4

Byte: hex A4.

This loads the high nibble into the accumulator again. When the program jumps here from address 007 the accumulator already holds it, but when it falls through from address 00A the accumulator holds the low nibble instead. Loading R4 here means both paths work.

Address 00D: WRR

Byte: hex E2.

WRR means write ROM port. It sends the accumulator to the port chosen by the last SRC, which is port 0. For H, it sends 4. The console holds on to it and waits for the second half.

Address 00E: LD R5

Byte: hex A5. This loads the low nibble, 8 for H, into the accumulator.

Address 00F: WRR

Byte: hex E2.

This sends the low nibble. The console now has 4 and 8, joins them into hex 48, and prints H.

Part 4: Moving to the Next Letter

Address 010: ISZ R1, loop

Bytes: hex 71, then hex 05.

ISZ means increment and skip if zero. It adds 1 to R1, the low nibble of the pointer. If R1 is not 0 afterwards, it jumps to loop at hex 005 to print the next letter. If R1 has just wrapped round from 15 to 0, it does not jump, and the program carries on to the next line.

The 7 in hex 71 means ISZ, and the 1 means register R1. Like JCN, the second byte is an address within the current page.

Address 012: INC R0

Byte: hex 60.

The program only reaches this line when R1 has wrapped from 15 back to 0. A register only holds 0 to 15, so on its own the pointer would go from hex 1F back to hex 10, and the program would print part of the message again. Adding 1 to R0, the high nibble, fixes that. Hex 1F becomes hex 20, just like 19 becomes 20 when you count in tens.

This is how the 4004 counts past 15. It uses two 4-bit registers and carries from one to the other by hand.

Address 013: JUN loop

Bytes: hex 40, then hex 05.

JUN means jump unconditional. It always jumps, and it can reach any address in all of ROM. The 4 means JUN. The remaining three hex digits, 0, 0 and 5, are the 12-bit address hex 005. After the carry, the program goes back to the top of the loop.

Part 5: Stopping

Address 015: done: JUN done

Bytes: hex 40, then hex 15.

This line jumps to itself, forever. The 4004 has no halt instruction. A real chip in a calculator never stops. When it has nothing to do, it loops. Programs written for testing used a jump to itself like this to park the chip.

The emulator notices a jump to the same address, which can never go anywhere else, and stops the run there. That is why it reports that it stopped at hex 015.

Part 6: The Message

Address 017: msg: DB "HELLO, WORLD! THE 4004 TURNS 55 TODAY.", 10, 0

DB means define bytes. It is not an instruction for the chip. It tells the assembler to put these bytes straight into ROM. The text in quotes becomes one ASCII byte per character. Then 10, which is hex 0A, adds a new line, and 0 adds the end marker.

That is 38 characters, plus the new line, plus the end marker, so 40 bytes in all, at addresses hex 017 to hex 03E.

The chip never runs these bytes as instructions, because the program always jumps around them. If it did run them by mistake, the H and E, hex 48 and hex 45, would be read as JUN 0x845, a jump to an empty part of ROM, and the program would go wild. In a 4004 program, data and code are just bytes in the same ROM.

Following One Letter with a Trace

You can watch every instruction run with the trace option:

python -m i4004 run examples/hello.asm --console --accessible --trace --quiet

Here are the first ten steps, which print the H:

Step 1, at hex 000: FIM P1, hex 00. Load hex 00 into register pair 1,
registers 2 and 3. No change.
Step 2, at hex 002: SRC P1. Send register pair 1 as the RAM and ROM port
address. No change.
Step 3, at hex 003: FIM P0, hex 17. Load hex 17 into register pair 0,
registers 0 and 1. Result: R0 now 1, R1 now 7.
Step 4, at hex 005: FIN P2. Fetch the ROM byte addressed by register
pair 0 into register pair 2. Result: R4 now 4, R5 now 8.
Step 5, at hex 006: LD R4. Copy register 4 into the accumulator. Result:
accumulator now 4.
Step 6, at hex 007: JCN 12, hex 00C. Jump to hex 00C if the accumulator
is not zero. Result: jumped to hex 00C.
Step 7, at hex 00C: LD R4. Copy register 4 into the accumulator. No
change.
Step 8, at hex 00D: WRR. Write the accumulator to the selected ROM
output port. Result: wrote 4 to ROM port 0.
Step 9, at hex 00E: LD R5. Copy register 5 into the accumulator. Result:
accumulator now 8.
Step 10, at hex 00F: WRR. Write the accumulator to the selected ROM
output port. Result: wrote 8 to ROM port 0.

Steps 1 and 2 say no change. Registers start at 0, so loading 0 into them changes nothing you can hear. SRC also sent hex 00, which was already the selected address. Step 6 shows JNZ the way the chip sees it, JCN 12. The 12 is hex C.

Further on, after the O in WORLD at address hex 01F, you can hear the carry from Part 4 happen:

Step 75, at hex 010: ISZ R1, hex 005. Add 1 to register 1, then jump to
hex 005 unless it became 0. Result: R1 now 0, did not jump.
Step 76, at hex 012: INC R0. Add 1 to register 0. Result: R0 now 2.
Step 77, at hex 013: JUN hex 005. Jump to hex 005. Result: jumped to hex
005.
Step 78, at hex 005: FIN P2. Fetch the ROM byte addressed by register
pair 0 into register pair 2. Result: R4 now 5, R5 now 2.

The pointer went from hex 1F to hex 20, and the next byte fetched is hex 52, the R in WORLD.

Stepping Through It Yourself

The debugger lets you run one instruction at a time and ask questions in between:

python -m i4004 debug examples/hello.asm --console --accessible

At the 4004> prompt, type s and press Enter to step one instruction. Type r to hear the registers. Type b done to set a breakpoint at the done label, then c to run until it gets there. Type h for the full list and q to quit.

Summary

  • Text is stored as ASCII bytes. H is hex 48.
  • The 4004 prints a byte as two nibbles, high first, using WRR twice.
  • SRC picks the port. It only has to be done once if the port never changes.
  • FIN reads a byte from ROM at the address in P0. That makes P0 a pointer into the message.
  • JCN, and its friendly names JZ and JNZ, make decisions by testing the accumulator.
  • ISZ counts a register up and loops. When it wraps, the program carries into the next register with INC.
  • The 4004 has no halt. A jump to itself parks the chip, and the emulator stops there.

Exercises

  1. Change the message to say hello to you by name. Assemble and run it. Does the program need any other change? Why not?
  2. Make the message two lines long by putting a new line in the middle: DB "HELLO, WORLD!", 10, "THE 4004 TURNS 55 TODAY.", 10, 0. Run it. Which part of the program makes sure the first new line is printed instead of being mistaken for the end?
  3. Remove the end marker, the , 0, and run the program. It still stops. Why? Hint: what is in ROM just after the message? Would you want to count on that in a real program?
  4. Change FIM P1, 0x00 to FIM P1, 0x10. Run it with --console 1 instead of --console. Why does that still work?
  5. Delete the INC R0 line and run the program with --max-cycles 2000 added, so it cannot run for long. Listen to the output. Can you explain exactly where it goes wrong?
  6. The message must end before address hex 100. Why? Which instruction makes that rule?
